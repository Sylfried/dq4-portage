## Interface d'origine : saisie (clavier, souris = tactile), fenêtres du terrain (30/10/2026, issues #38 #39)
- **Message moteur <- Unity** (`MenuPort.Send`, `OUC_Input`) : `[1, numéro de bouton, manette]`. Numéro >= 0 = appui sur ce bouton (le numéro est l'identifiant de commande du moteur : menu racine Objets 2, Magie 1, Carac. 4, Divers 5) ; `[1, -1, manette]` = entrée de manette seule, que le moteur n'exploite (déplacement de SON curseur) que s'il a une grille, c'est-à-dire s'il a envoyé la cmd 2 `[colonnes, rangées, nombre]` (ex. Oui/Non 1 x 2, menus de combat). Sans grille elle est ignorée : le curseur d'un menu « tactile » est donc local à Unity. Bits de manette : bas 1, haut 2, droite 4, gauche 8, A 16, B 32, X 64, Y 128.
- **Toucher** (`MenuPortItem.Update`) : appui = état « appuyé » du bouton + SE 300 ; relâchement sur le même bouton = `Send([1, buttonId (+0x48), gamepad (+0x4a)])`. `buttonId` / `gamepad` de chaque nœud sont lus par l'export (`parts.gamepad`). Certaines fenêtres exposent une grande zone `(-1, Y=128)` (fenêtre des personnages) : elle est cliquable comme sur mobile, mais le bouton dont la profondeur (Y monde du nœud) est la plus élevée l'emporte (à égalité, la fenêtre la plus récente).
- **Quelle fenêtre a la saisie** : le moteur renvoie cmd 6 à la fenêtre qui attend la saisie ; l'indicateur mémoire `this+0x50` ne couvre pas Oui/Non, d'où le critère `entree` (cmd 6 vue à l'image) en repli (`Moteur.menus_saisie()`, `menu_actif()`). Plusieurs fenêtres peuvent attendre en même temps (menu racine + plaques) : la souris regarde toutes, la plus récente d'abord.
- **Fenêtres du terrain** : les ports 2 à 11 (types 1 à 11 : or, personnages, menu racine, etc.) sont créés par le moteur AVANT que l'observateur de l'interface ne s'attache ; `Gestionnaire.rejouer(ui)` les recrée à partir de l'état déjà reçu (sinon seul le premier menu ouvert plus tard apparaissait).
- **Fenêtre de message du terrain** (type 0, cadre z -165..-39 en repère portrait) : en 16:9 elle est descendue au bas de l'écran (z -362, comme les types 1 à 3 du combat) et le Oui/Non (type 1, juste au-dessus) la suit ; elle reste à sa place si une autre fenêtre occupe le bas. `--msg-origine` garde la position d'origine.
- **Textes** : séquences `@cN` = couleur de la palette N, valable jusqu'à la suivante, y compris sur les lignes suivantes (textes des emplacements de sauvegarde).
- **Menus : textes, boutons sombres, taille (31/10/2026, retour d'essai « textes décalés », « boutons sombres », « UI plus grande »)** :
  - **Ancrage du texte** (`TextMesh.anchor`) : 0-2 = haut, 3-5 = milieu, 6-8 = bas du bloc ; l'ancrage bas pose le bas du texte au point donné (avant : traité comme un ancrage haut, texte sorti des boutons du menu racine, de BattleRoot et BattleAction). `AddTextMesh` reçoit `eIndent.CalcLocalPosition(bouton, indent, ...)`, qui lit `Mesh.bounds` du bouton : l'export de la mise en page DOIT émuler `Mesh.get_bounds` et `Screen.get_width/height` (1080 x 1920), sinon les textes de 8 types de fenêtres (Oui/Non, menu racine, BattleRoot/Action/Go/ChangeButton, Chapter2Status, FightStadiumAbort) sont mal placés. **Un `ui_layout.json` produit par une ancienne version de l'extracteur est faux : le régénérer avec `tools/ui_il2cpp/generate_ui.py` (les tests du cloud doivent utiliser la mise en page de l'extracteur du dépôt).**
  - **Boutons « sombres »** : les fenêtres étaient dessinées fenêtre par fenêtre ; le fond translucide (profondeur y = 0) de la fenêtre des personnages (`type 4`, 457 unités de large) recouvrait les boutons du menu racine (y = 8) dessinés avant lui. Unity trie les objets transparents par profondeur sur la caméra : `Rendu.dessiner` trie maintenant tous les éléments des fenêtres par (profondeur, fenêtre, ordre).
  - **Taille** : `UI_ZOOM` (1,12). Les fenêtres proches (moins de 60 unités) forment un groupe ; un groupe du bas / du haut / du milieu est agrandi autour du bord bas / haut / centre de l'écran. Le coefficient est réduit jusqu'à 1 si un groupe sort de l'écran ou en recouvre un autre (`Jeu._ui_echelle`) ; zones tactiles (`ui_tf`) et projection des plaques de monstres suivent.
- Non résolu : le texte d'action « Attaquer / ▼ / cible » sous le bandeau des personnages n'a pas de cadre, cadre de titre (type 54), niveau « ? » du deuxième personnage dans les plaques.

Un personnage créé (paquet 12) est visible par défaut ; le moteur envoie 14 `[n, 0]` pour les cacher (vu à l'image 1) et `[n, 1]` pour les montrer (héros et équipier à l'arrivée sur la carte du monde). `Etat.sprites[n]['vis']`, la visionneuse ne dessine pas un sprite caché. ## Son : conteneur AKB, paquets 35/36/37 (30/10/2026, issue #17 / #42)
- **Fichiers** : `assets/sound/BGM01..BGM51.akb` (51 musiques) et `SE0300..SE1170.akb` (634 bruitages) dans l'APK de données (`split_UnityDataAssetPack.apk`). Lus par `libsdlib_android.so` (`akbMaterial*`), joués côté Unity par `Sound.PlayBGM / StopBGM / PlaySE / StopSE`.
- **En-tête AKB** : `0x00` `AKB ` ; `0x04` u16 version ; `0x06` u16 taille d'en-tête ; `0x08` u32 taille du fichier ; `0x0c` u8 codec (**2 = MS-ADPCM** pour les bruitages, **5 = Ogg Vorbis** pour les musiques) ; `0x0d` u8 canaux ; `0x0e` u16 fréquence ; `0x10` u32 nombre d'échantillons ; `0x14` u32 début de boucle ; `0x18` u32 fin de boucle (0 = pas de boucle) ; `0x20` float volume propre au fichier (0,65 à 0,9 pour les musiques). Bloc d'extra à `0xc0` : u16 `0`, u16 taille de bloc ADPCM (`0xc2` : 22 mono / 44 stéréo = 32 échantillons par bloc), u32 échantillons, u32 début de boucle. Données à `0xcc` : Ogg complet (codec 5) ou 4 octets puis blocs MS-ADPCM (codec 2).
- **MS-ADPCM** : coefficients standard de Microsoft (256/0, 512/-256, 0/0, 192/64, 240/0, 460/-208, 392/-232), en-tête de bloc = indice de prédiction, delta, échantillon 1, échantillon 2 (regroupés par canal), sortie dans l'ordre échantillon 2, échantillon 1, puis les quartets (poids fort d'abord ; en stéréo ils alternent gauche / droite). **La prédiction `(a*c1 + z*c2) >> 8` est une division entière vers zéro** (pas un décalage arithmétique) : c'était la seule différence avec ffmpeg. Vérifié : 53 bruitages sur 53 identiques à `ffmpeg -acodec adpcm_ms` (écart 0). Musiques : `soundfile` (libsndfile) et ffmpeg donnent le même signal (écart <= 1).
- **Paquets** : **35 `[id]`** = `PlaySE(id)` (`SE%04d`) ; **36 `[id]`** = `StopSE` ; **37 `[id]`** = `PlayBGM` (`BGM%02d`) ; **valeurs >= 0x4000** = `StopBGM` (`SoundManager::stopBgm` envoie `0x4000 | durée`, `battleStop` 0x4008 ; Unity ignore la durée : arrêt immédiat) ; **0x1000 <= valeur < 0x4000** (`SoundManager::playRestart`) = `PlayBGM(valeur - 0x1000)` avec reprise : Unity mémorise le numéro de la musique en cours (`Sound` statique +4, drapeau +0) et `Sound.SystemUpdate` relance cette musique (depuis le début) dès que le morceau (jingle sans boucle) est fini (31/10 : avant, la visionneuse prenait ces valeurs pour un arrêt). `StopBGM` ne remet pas l'état du jingle à zéro : un arrêt reçu **pendant** un jingle à reprise fait repartir la musique d'avant (#230, audit SND-05) ; un morceau sans boucle arrivé à sa fin, redemandé, repart (SND-06). Vus : musique 14 = village de départ, 5 = carte du monde, 30 = combat, 23 après la victoire (précédée d'un arrêt 16392), puis retour à 14 ; bruitages 307 = pas, 300 = valider / page de message suivante (envoyé par le moteur), 400 à 415 / 804 / 805 = combat, 409 = fanfare, 306 / 609 = fin de combat.
- **Qui joue quoi (31/10, issue #54)** : analyse de tout `libil2cpp` (appels directs et sauts de queue vers `Sound.PlaySE` D15128 / `PlayBGM` D15438, `SoundControl.Play` / `StreamPlay`, `CreateSound`) : Unity ne joue lui-même QUE le bruitage 300 (`MenuPortItem.Update`, `TouchPad.internalUpdate`, `InputName.Update`) ; tout le reste (portes 309, jarres / coffres = id lu dans la définition du meuble `TownFurnitureObject::openObject`, escaliers, 1124 dans `NonBattleActionManager::execute`, avec l'effet d'écran 3 « voyage », attaques 400-415 / 709 / 714...) vient du moteur par les paquets 35 / 36 / 37 (`SoundManager::playSe`, `Sound::sePlayDirect` = paquet 35 `[id]`, `playBgm` / `play` / `playStart` / `playRestart` / `stopBgm` = paquet 37). Aucun bruitage de début de combat n'est demandé : seule la musique (30) change. Les 634 fichiers `SE*.akb` se décodent tous (volume propre 0,25 à 0,6) ; **14 bruitages bouclent** (311, 327, 328, 330, 354, 1101, 1104, 1108, 1132, 1141, 1142, 1143, 1152, 1153) jusqu'à l'ordre d'arrêt (paquet 36) : la visionneuse les boucle maintenant (coupés au bout de 120 s au cas où l'arrêt ne viendrait pas).
- **Bouton de menu** : le bruitage 300 de l'appui sur un bouton est joué par Unity (`MenuPortItem.Update`), pas par le moteur : le moteur ne l'envoie que pour la validation d'un message. La visionneuse le joue à l'appui d'un bouton (souris) et à la validation / annulation au clavier. Déplacer le curseur ne produit aucun bruitage.
- `snd_vol.dat` (1171 flottants dans `assets/sound` ; indice = numéro de fichier `BGM%02d` ou numéro de bruitage `SE%04d`) : **appliqué depuis #238** (`Son.vol_snd`, volume joué = en-tête du fichier x `snd_vol` x curseurs). 49 musiques de 0,7 à 0,95 (BGM14 et BGM20 à 1,0), SE0409 (fanfare) à 0,6, tout le reste à 1,0. Non étudié : fondus entre musiques (`PlayBGM` côté Unity), bruitages 3D / positionnels (audit son du 04/11/2026 : aucun fondu ni positionnement relevé).

## Fenêtre de carte (type 25), caméra des villes, vitesse du héros (31/10/2026, #28)
- **Fenêtre type 25** (`Make_CityMap`, moteur `FieldImageMap::open`) : commande 12 `[12, code, valeur]` (`setItemCode`) : codes 1 / 2 = x / y du joueur en pixels du plan de 256 x 192 ; **code 3** = liste des lieux découverts, **code 4** = un lieu spécial, **code 5** = voile ; pour 3 et 5, les messages suivants sont des **données** (un court par entrée), pas des commandes : x = octet bas, y = octet haut pour un lieu (code 3) ; pour le voile (code 5), 16 courts, **un bit par bloc de 10 x 10 pixels non exploré** (bit levé = encore voilé), grille de 16 x 16 blocs qui commence en **x = 48, y = 16** (grille centrée sur le centre (128, 96) du plan de 256 x 192 ; x = 56, écrit jusqu'en #32, décalait les zones explorées de 8 pixels : la plume se retrouvait hors de la zone dévoilée). Le code 4 est un demi-mot compacté (`x | y << 8`, pixels du plan de 256 x 192), jamais reçu en début de partie ; affiché depuis l'audit de fidélité du 01/11/2026 (croix rouge, voir plus bas). Le type 26 est la grande carte (plan 1024 x 1024 centré sur le héros).
- **Rendu d'origine du voile** : texture `dsdq4wmap01m` (RGBA 256 x 192) posée sur le plan en filtre « plus proche voisin » ; les blocs voilés sont ceux dont le bit est levé. Les lieux sont des carrés rouges de 4 unités (`BlinkMapSymbol`) dont la transparence suit |1 - (t mod 4) / 2|. Coordonnées de la mise en page : le plan occupe x de -225 à 225, z de 400 à 337,5 ; coordonnées d'objet = x + 225, z - 400. *(Corrigé le 01/11/2026 pour le type 25 : le plan de 450 x 337,5 est posé en (2, -2) à l'échelle locale 0,99, soit x de -223 à 222,5 et z de 398 à 63,875 ; voir plus bas.)*
- **`TownCamera`** (objet statique `_ZN10TownCamera11m_singletonE` de `libdq4core.so`) : +0x34 limite gauche, +0x38 limite droite (en 1/4096 de tour) : < 0 rotation interdite (-182 dans les grottes), 0 libre, > 0 bornée (5461 = 120 degrés) ; +0x3e verrou.
- **Vitesse du héros** (variables statiques en virgule fixe, par pas de moteur) : `TownPlayerAction::walkSpeed` = 819, `walkSpeed2` = 655, `FieldPlayer::Speed` = 12288. Les réécrire à chaque pas accélère le déplacement du héros seul (distance par pas mesurée proportionnelle) ; la pose du héros est liée au temps (3 pas par pose, cycle 1-2-1-0) et n'est pas accélérée. Accélérer les pas du moteur accélère aussi PNJ, animations et scripts.
- **Compagnons en ville** (`TownPartyAction`, 01/11/2026, #30) : `normalMove` décale à chaque pas du héros un historique de positions (`[this]`, entrées `Fix32Vector3` de 12 octets, 126 entrées) et y écrit la position du héros ; les compagnons lisent l'entrée `k x espacement`. L'espacement est un statique en `libdq4core + 0x24de94` (8, ou 10 si `[global + 0x278] == 10`), fixé par `AdjustArray(n)` à chaque image (réorganise l'historique quand n change, branche spéciale pour n = 8). Le nombre de membres est `[objet + 0x23c]` (objet pointé par le GOT `0x23d920`). `TownPartyAction::execute` est vide (`ret`). Comme l'espacement compte des images, la distance des compagnons est proportionnelle à la vitesse du héros. **Carte du monde** : `FieldParty::getMemberPosition` lit `array + i x 0x54` (7 entrées de 12 octets, constante dans l'instruction), `normalArray` décale 159 entrées. Les PNJ n'utilisent pas ces historiques.
- **Fenêtres de message de combat** : `ui_layout.json['message']['types']` 2 et 3 ont `scale` 0,9 (490 texels dans 441 unités de toile) : texte 10 % plus petit que dans les types 0 et 1.

## Boutiques en ville (type 24), vitesse en diagonale, numéros d'éléments (01/11/2026, #32)
- **`TownImageMap::execute`** (`0x1e88bc`) gère la carte d'une ville : état `[+8]` = ouverte, `[+9]`, `[+0xa]`, `[+0xb]` = mode liste des boutiques. Fenêtres créées avec la carte : port 12 type 25 (plan), port 13 type 24 (`Make_ShopMap` : liste des boutiques, cachée au départ), port 14 type 22 (bouton retour). Indice et nombre de boutiques : deux statiques locaux (`libdq4core + 0x2750c4` et `+ 0x2750c8`, demi-mots). Haut de la manette (`[1, -1, 2]`) envoyé à la fenêtre 12 : bascule plan / liste (le plan se cache, la liste s'affiche et prend la saisie) ; droite (`[1, -1, 4]`) / gauche (`[1, -1, 8]`) sur la fenêtre 13 : boutique suivante / précédente (le moteur boucle) et le texte de la fenêtre change. Contenu type 24 : `(0,0)` nom de la boutique, `(0,1)` objets (un par ligne), `(0,2)` prix, `(0,3)` « i/n » (absent s'il n'y a qu'une boutique).
- **`NormalControl::execute`** : à l'appui du bouton de carte (bit 7 de la manette), le mot de drapeaux pointé par le GOT `0x9f8` (probablement celui du `CommandWindow`, dont le bit 5 est la permission de la liste, `setShoplistPermit`) décide : bit 4 levé = `openMap`, sinon bit 5 levé = `openShopList`. **Non vérifié** : dans la visionneuse la touche de carte ouvre toujours la carte (`FieldImageMap` / `TownImageMap`), puis la liste par le haut de la manette.
- **Vitesse en diagonale** : `FieldPlayer::move` (`0x1ed428`) : 8 directions (`(angle >> 13) & 7`) ; les droites lisent `FieldPlayer::Speed` (3,0), les diagonales les deux constantes locales en `+ 0x27520c` / `+ 0x275210` (2,0), le ballon `+ 0x275214 / 0x275218` (3,0). Initialisés au chargement par `0x1eec50`.
- **Numéros d'éléments (`id` des nœuds) de `ui_layout.json`** : ils dépendent de la génération de l'extracteur (ex. marqueur de la carte de ville 1527 puis 1531) ; ne jamais les coder en dur, chercher par dessin (`part`) ou par rôle.
- **Messages du terrain** : hauteur de ligne du canevas 28 unités (statique `[L + 0x2523a0]` = 3 en terrain, 4 en combat ; `obj_msg + 0x42` hauteur de ligne, `+ 0x4a` défilement) ; le cadre du type 0 fait 3 lignes + marge.
