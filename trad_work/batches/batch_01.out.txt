Battle start effect (Capture.BattleEffect of the Unity layer): a screen capture, cut into 32 columns of chunks, shatters and falls
row after row, from top to bottom, then darkens to black.

Reproduces the game's rules, one update per frame (30 Hz):
  * two counters: A (0, 1, 2...) and B (0 until frame 21, then it follows A with a 20-frame lag); on every frame and for each chunk, the game randomly picks
    (1 chance in 3 for B) the counter that drives that chunk;
  * a chunk in row r moves if either counter exceeds r; the fall speed is -0.001953125 - (32 - r - column + counter) * 0.0015625
    (in normalized screen coordinates, -1..1), half of that when it is the "lagging" counter that made it move; the left and right edges move closer
    by about 0.001 per frame (the chunk narrows) and the chunk drifts 0.002 to the left;
  * a chunk's opacity decreases by 8/255 per frame of movement;
  * when A exceeds half the height, the capture's brightness drops by 2/56 per frame; the effect stops when A exceeds 56.
The original game cuts the portrait screen into 32 x 56 square chunks (56 = 32 / 0.5625). On a 16/9 screen we keep square chunks (32 x 18) and each row
takes the place of 56 / 18 original rows, so the timing (57 frames) is the same.

Captures battle results for the battle history: defeated enemies, gold won, experience gained.

    sensor = BattleSensor(engine)         # once, after the Engine is created (installs READ-ONLY hooks in the emulator; writes nothing to the engine's memory)
    for battle in sensor.do_update(engine): ...  # ONCE per engine frame, after engine.step; returns the battles FINISHED at this frame (most often an empty list)

Each battle: {'t': game time at the end (1/60 s, status::g_Game + 4), 'ennemis': [{'nom': 'Gluant', 'total': 3, 'vaincus': 1, 'fuis': 1, 'disparus': 0}, ...] (one element per species, in order
of appearance; what remains, total - vaincus - fuis - disparus, is still there when the battle ends: the party fled or was defeated), 'or': int, 'xp': int, 'issue': 'victoire' | 'fuite' | 'defaite',
'objets': [{'nom': 'Herbe médicinale'}, ...] (the items the game gives the party at the end of the battle: "Le gluant laisse tomber un coffre au trésor !")}. Gold and experience: those of the game's victory message,
0 for a flee or a defeat (the engine does not award them).

Method (ESTABLISHED by reading the disassembled engine and then by measurement: see tools/test_battle_history.py):
- DEATHS are noted by a hook on BattleActorManager2::execMonsterDeath(this, i), the function the game calls once per defeated monster (not for a monster that flees or vanishes) and which adds
  the monster's experience to g_Party + 0x2f8 and its gold to g_Party + 0x2fc. These are the two counters that BattleExecVictory01 / BattleExecVictory20 read to build the messages "N points d'experience" and "N pieces d'or"
  (getBattleExp / getBattleGold, after the possible doubling by reflectBattleExp / reflectBattleGold): so we take the largest of their readings from one frame to the next, until they are reset to zero.
- Monsters that FLEE and those that VANISH are noted by two hooks in the middle of BattleActorManager2::checkDeathMonster (the routine that, every frame, reviews the dead, fled or vanished monsters;
  it counts them inline in +0x7d24 / +0x7d28, BattleEndTask::initialize reads them, and it calls execMonsterDeath only for a dead one): just before the increment of the flee counter
  (+0x98, `ldr w8, [x23, #0xd24]`) and of the vanish counter (+0xc0, `ldr w8, [x23, #0xd28]`), w20 is the monster index (same index as for execMonsterDeath). Each monster goes through there only once
  (a mask of the monsters already processed, +0xd30, guards against repeats).
- The ITEMS won are given by BattleExecVictory32::setup (the task that follows victory: "laisse tomber un coffre au trésor !", "Ragnar l'ouvre.", "Il contient un arc de chasseur !"): it calls
  PartyStatus::giveItem(item = task + 0xc), which returns the index of the member who takes it, or -1 when it goes into the bag (measured: "Ragnar met l'arc de chasseur dans le sac." with -1); in both cases the item is
  obtained. Hook right after the call (+0x28, `cmn w0, #1`): x20 = the task. NOT VERIFIED: what the game does when the bag itself is full. The item name is requested from
  the engine itself (TextAPI::extractText(buffer, 0x4000000 | number), which is what the game does for the "item name" macro), between two frames, never inside a hook; the ";" (the patch's name break marker) is removed.
- The START is PartyStatus::startBattle, the END is Global::endBattle(bool) (true argument = party wiped out), the VICTORY BattleExecDefeatMonster::initialize (the "all enemies are defeated" routine,
  which awards the experience), the FLEE BattleExecEscape::setup (called on every flee ATTEMPT, successful or not: a successful flee is therefore "attempt made, no victory, battle ended").
- The ENEMIES are read every frame in g_Monster (12 slots of 0x538 bytes starting at +8; +0x4f8 = monster number, -1 if empty; +0x4fc = group number): one monster = one occupied slot;
  the species is the monster number. Reinforcements called during the battle are added to the total.
- The NAMES are those of the monster plates that the engine sends to Unity (Engine.ui, window of type 31: "Rat volant", "Gluant\n\n\t×3" -> "Gluant"), associated with the groups in order (plate j carries the
  j-th group), only when there are as many plates as groups and before the first death. Without a plate (surprise attack: the game does not display any; plates for a different number of groups), the name
  is requested from the engine itself at the end of the battle, by monster number (TextAPI::extractText(buffer, 0x6000000 | number): "londuleux", "armure ;errante", "scara$somniaque" -> "Londuleux",
  "Armure errante", "Scara-somniaque"); "Monstre" if the engine does not answer.
Everything is guarded: an error returns nothing and is written only once to the console. A battle whose start was not seen (savestate loaded mid-battle, sensor created during a battle) is never
reported: better to say nothing than to say something false.

Battle speed: the engine clock during a battle (pure logic, no window or engine: tested by tools/test_battle_speed.py).

Principle: the original engine advances in steps of 1 / 30 s (Time.fixedDeltaTime). The viewer makes it perform 1, 2 or 3 times more steps per real second during a battle (setting "Vitesse de combat":
Manuel and Normal: 1; Rapide: 2; Tres rapide: 3), instead of changing anything in the engine. Each step is exactly the game's own: the result of a battle (damage, action order, random draws, delays counted in
frames) therefore does not depend on speed; only the real duration changes. Everything the viewer animates during a battle is counted in engine steps (`engine.frames` + fraction `alpha`): damage numbers,
plate shakes, fades, battle start effect, message scrolling (written by the engine), 3D model animation; they therefore follow the accelerated clock.

What is NOT accelerated, on purpose:
  - music and sound effects: they are played by pyglet at their normal speed (real time, file duration); only the trigger TIME of a sound effect follows the engine. If acceleration makes the same
    sound effect arrive several times in the same displayed frame, it is played only once (`sounds_to_play`);
  - key READING while the player is being waited for (command menu, target choice, "Manuel" message waiting for a key): the engine runs there at the setting's speed (monsters keep their idle animation
    at that speed) but only steps at normal cadence (one every 1 / 30 real seconds) read keys; the others are "muted" (window.tick(mute=True)): cursor and key repeat unchanged;
  - the accelerator key: it only multiplies walking and the camera outside battle. `factor` deliberately has no parameter for it.

## FILE dq4_pc/core/encounters.py

Random encounters, day / night clock and walking speed (#45, #163).

What the original game does (read from the disassembly of libdq4core.so):
  - Every engine frame where the hero's position has changed (world map: FieldPlayerDoku::checkDokuDamage; towns and dungeons: TownDamageFloor::checkDamageFloor, both through
    CommonWalkDamage::checkWalk) calls `Encount::execWalk`. It counts 16 calls, then launches `Encount::exec` (once, or five times when [+0x2c] is non-zero).
  - `Encount::exec` calls `CountDown::exec` (0x1f454c): the counter [Encount+0x134] loses `2 x [Encount+0x144]`; the encounter is triggered when it becomes negative (state [+0x1c]: 0 -> 1 -> 2, then `brew`
    and `Global::startBattle`). The counter is drawn by `CountDown::setup` (0x1e00 + table[rand(31)]) on each map initialization (`Encount::setup`, so also on return from a battle);
    its loss per call (`[+0x144]`) comes from `TileSubtractValue[tile] x table du terrain >> 8` (setTileIdRate / setLandType, recomputed on every `exec`).
  - None of this depends on real time: the game counts ENGINE FRAMES where the hero moves (so steps).

What the viewer does: accelerated walking ("Vitesse de marche", accelerator) makes the engine run `a` times faster, so the hero takes `a` times more steps per real second and, without correction,
`a` times more encounters per second. We want (1 + a) / 2: x1 unchanged, x2 = 1.5 times, x3 = 2 times, x4 = 2.5 times (walking speeds up without battles becoming unbearable). Each step therefore counts
(1 + a) / (2 a) times what it used to count: `factor_per_step`. The correction is applied to the engine's own counter (a hook on the write in `CountDown::exec`, see Engine._encounter_hooks),
not by an extra draw: the counter's loss on each call is multiplied by this factor (accumulated fractions: `Reducer`), the distribution of monster groups, the counter draw and everything
else stay the game's own. Only when a > 1 (x1: the hook does nothing).
